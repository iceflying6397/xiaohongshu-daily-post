# 小红书每日图文

每次调用制作一条图文，流程只有两步：先写文案与生图提示词，再生成配图。默认连续完成两步；用户明确只要第一步或要求先审稿时，按其要求停止，不另设默认审批环节。此技能不发布到小红书。

## 开始前：确认主题与落盘位置

- 从本次请求和正在继续的图文中确定主题。没有主题，或主题的含义、范围存在会影响内容的疑问，先询问用户；得到答复前不要分配序号、写稿或生图。普通排版和风格选择自行处理。
- 读取当前项目的 AGENTS.md，确定当前工作区根目录。不要把内容写到技能安装目录，也不要固定使用技能作者的个人路径。若当前目录无法明确识别为目标项目，先询问用户目标位置。
- 使用用户当前时区的日期，格式 YYYY-MM-DD。优先采用会话的客户端日期与时区，缺少时再查询；不要直接采用执行机器的日期。用户指定其他发布日期时优先采用指定日期。
- 新建图文时，用本技能的 `scripts/prepare_post.py` 检查当天目录；提供明确的 `--root` 和 `--date`。默认只检查，`--reserve` 才分配目录。使用可用的 Python 3；系统 Python 不可用时可查找 Codex 内置运行环境。
- 区分“已有内容”和“空目录”：只有忽略 .DS_Store 后完全空白，或仅有空的配图目录，才可作为新图文使用。任何文稿、提示词、图片、制作标记或其他素材都表示该序号已占用；未完成的图文也不能覆盖。优先用最小的空白序号；没有空白序号时，使用现有最大序号加一。发现含糊的目录或符号链接时不要写入。
- 写入前先向用户明确说明：“本次制作 YYYY-MM-DD 的第 N 条图文，主题是……”。随后用 `--reserve` 预留位置；如果并发工作导致分配结果变化，先更新说明，再写入。保留脚本返回的 reservation_token，用于完成后的清理。检查与说明不是请求批准。
- 用户要求继续某条图文时，沿用其原日期和序号，不另分配；优先结合刚才的上下文识别。如果存在多个可能的未完成图文，先询问。只补缺失图片；修改既有文稿或图像须有用户的修改要求，重制图片可保存版本文件。

## 第一步：纯文字文案与对应生图提示词

### 文案

- 保存为 `日期/N/内容文稿.txt`，UTF-8 纯文字。技能说明和提示词可以使用 Markdown，发布文案本身不能使用 Markdown 排版。
- 文稿包含标题、正文、话题标签，使用换行和“01｜……”等纯文字章节组织清楚的脉络。禁止 Markdown 标题符号、星号加粗、代码围栏、表格及 Markdown 链接；话题中的 # 标签正常保留。
- 手机阅读排版：正文每个完整句子独占一段，句末标点（。！？及对应英文标点）和紧随的表情之后换行，再留一个空行，即相邻句子之间使用两个换行符。不能只在章节或原段落之间空行，也不能把两句话接在同一段。标题、章节名和列表要点各自独占一段，与前后内容之间同样留一个空行；不因逗号、顿号、冒号或分号而拆行。
- 句子自然、完整，长短搭配，保留解释、原因和例子之间的衔接；不要为了排版把一句连贯的话拆成多个短句、口号或碎片。同一个意思可用逗号和关联词组织成通顺的复句，只有转换意思或句子过长影响理解时才拆句。“简短”指全文精炼、不重复，不代表每句话都要短；也不要为了加长句子堆砌内容。
- 面向小白，简短、通俗，一篇只讲清一个核心主题；默认正文约 300–600 个中文字符，按主题和用户要求调整。
- 多用贴切的生活类比和具体例子；先给直观解释，再用例子说明，最后写使用场景或关键提醒。类比不能替代准确概念，示意输出或虚构例子要说明其示意性质。
- 增加小表情与小符号的密度：标题和每个章节名都配一个贴合主题的 emoji，正文通常每 1–2 句配一个，举例、步骤和关键提醒优先配上，例如 🤔、🛠️、🔍、📝、✅、💡、📌。适当使用“→”“｜”“①②③”等纯文字符号帮助串联流程、区分要点；同一句一般不超过两个 emoji，流程箭头和编号按表达需要使用，避免连续堆叠装饰或给每个词加表情。
- 结尾固定使用以下话题标签，按原样和原顺序作为文稿最后一行，与正文之间空一行；保留大小写与“[话题]#”格式，不加引号，不自行增删或替换，除非用户另有明确要求：
  #深圳且曼Ai产品经理就业班[话题]# #求职[话题]# #就业[话题]# #AI[话题]# #实习[话题]#
- 准确核对概念，必要时查询原始文档。不要把“不一定”写成保证。参考来源和制作备注单独保存为 `制作备注.md`，不要混入供发布的正文。

正文排版示例（每句话独立成段，句子之间留一个空行，句意保持完整）：

```text
01｜像给 AI 配一间厨房 🍳

如果把模型想成负责理解要求、决定下一步怎么做的厨师，那么 Harness 就像配套的厨房，为它提供工具和操作流程。🛠️

02｜任务怎么往前走？🔄

模型先选择要执行的动作，再由 Harness 调用工具并把结果交回来，模型看完结果后就能继续判断下一步怎么做。🔍

比如查完一份资料后，模型可能发现还缺一个信息，于是继续查找，再根据拿到的结果整理回答。
```

### 配图提示词

- 保存为同条图文下的 `配图/生图提示词.md`；绝不是项目根目录中共享的配图文件夹。
- 每条完整图文至少配 6 张发布图片，包含 1 张封面和至少 5 张内容图；按文案主题拆分概念、构成、具体例子、使用场景和关键提醒，必要时将一个章节拆成多张，避免为了凑数量重复内容或增加无依据的结论。用户明确只要求重做某张图片或先看封面时，本次只完成指定范围，不自动扩展为整套重制。
- 封面的文字只保留一个醒目的主题问题，例如本项目第 9 条只写“Skill 是什么？”，不加副标题、核心解释、要点清单、页码或系列标记。用大字号、清晰层级和充足留白突出主题，详细解释放在内容图中。
- 封面主题始终是视觉主角，小机器人及其情景是配角。根据标题长度、换行方式、文字位置、留白和视觉平衡，有机调整机器人的位置与大小，不规定任何固定角落、固定占比或统一布局；机器人和情景不遮挡主题，也不抢走标题的注意力。
- 封面可以加入贴合主题的简单场景、必要道具或可爱互动，让小机器人更生动有趣，例如在电脑前思考、与物品或小动物互动；这些只是创作方向，不是必须出现的元素。根据主题选择表情、动作、情景和趣味点，在简洁与趣味之间取得平衡，避免机械复用站姿、招手、托腮或某个场景，也避免加入无关互动和繁杂装饰。此创意指导适用于封面；内容图仍以解释文稿为目的。
- 项目根目录下的 `角色素材/小机器人/封面版式参考.png` 仅用于参考主题优先、角色辅助、画面简洁的视觉层级，不是需要复制的固定模板；每次按主题重新组织文字与情景，不沿用其固定位置、大小或动作。角色身份仍以 A 标准形象为准。
- 小机器人采用项目固定的角色形象：生成前读取项目根目录下的 `角色素材/小机器人/角色设定.md`，使用其中已由用户选定的标准参考图和多角度图作为实际图像参考，不仅靠文字描述维持一致性。头部轮廓、面屏、五官、天线、耳部、身体比例和配色保持一致，可以按内容改变表情、动作和必要道具，不另造新角色。若尚未选定，按用户要求先提供备选、等待选择，再制作多角度参考图和后续配图，不擅自把候选当作最终形象。
- 每张列出发布顺序、对应章节、预期文件名、完整生图提示词与需显示的准确文字。命名按发布顺序为 `01.png`、`02.png` 等。
- 每条提示词均可独立使用，包含主体、构图、统一风格、颜色、比例、文字内容与位置以及必要的避免事项。
- 图片要解释同一个核心概念，图上的结论、例子与文稿对应。正文可以稍详，图上只留核心短句；不要凭空添加数据、温度数值、品牌或额外结论。
- 默认竖版 3:4，目标约 1080×1440，中文清晰大字号，四边安全留白。整组保持同一配色、字体感觉和角色。没有其他要求时可用奶油白底、蓝橙配色、简洁手绘小机器人；用户指定风格优先。
- 默认按完整排字成品准备提示词：要求生图工具准确呈现所列中文。若使用先生成底图再排字的路线，要把后续排字工作完成，不能只交付没有文字的底图。

检查文案精炼易懂、句意连贯完整、纯文字格式与图文对应关系，并逐段确认每句话单独成段且句子之间恰好留一个空行、没有过度切成短句、表情与小符号分布自然、末行固定标签完全一致后，报告第一步已完成，并继续第二步，除非用户要求停在第一步。

## 第二步：生成、检查并保存配图

- 使用内置 imagegen 生成图片，遵守当前环境的 imagegen 技能和工具说明。不要用手工形状、占位图替代用户要求的生图成品，也不要擅自切换 API / CLI。
- 每张图片单独生成。优先完成封面或一张能建立统一风格的图，检查后把该图作为其余图片的风格参考。使用本地图像作参考前先查看它。
- 可用子代理并行处理剩余独立图片，最多同时进行 3 个生图任务；每个任务只写自己负责的目标文件，主代理统一验收。网络不稳定时减少并发，保留成功输出，集中重试缺失图片。
- 生成结果通常在 Codex 的生成图片目录；取得工具实际返回的本地路径后，复制最终图片到当前图文的 `配图/`，不能只留在默认生成目录。复制采用不覆盖方式，目标已存在时先检查。
- 实际尺寸可略有偏差，要求整组比例与尺寸一致，中文在手机上易读。逐张查看并核对：文字准确无乱码、无裁切遮挡；概念和例子正确；章节匹配；角色与选定的标准参考图一致，配色一致。封面另检查是否只保留一个主题问题，角色位置是否与文字排版自然协调，简单情景与互动是否适合主题；缩小查看时，第一眼应读到主题，角色和场景保持辅助地位，画面简洁且有趣；整套交付时检查发布图片至少 6 张，旧版本和备份不计入数量。
- 有错误时进行针对性修正；网络失败时仅重试缺失的图片，每次调用每张最多额外重试一次。不要覆盖成功图片，也不要无限重试。用户明确要求继续时，可以对仍缺失的图片开启新一轮重试。
- 工具持续失败时，明确列出已完成和缺失文件，保存简短 `配图/生成记录.md`，说明实际错误；不要声称全部完成。备用 API / CLI 只在用户明确选择后使用。
- 全部计划图片都存在且检查通过，才宣布该条图文内容生产完成。更新制作记录，清除自己创建的制作标记：用脚本的 `--release N --token TOKEN`，仍提供原来的 root 和 date；不能清除其他任务的标记。若只完成第一步或存在失败，保留标记，便于继续制作。
- 结束时必须指出具体日期与序号：“YYYY-MM-DD 的第 N 条图文内容已生产完成”，并提供文稿和配图文件夹链接，简述图片数量。若有缺失，改为明确说明该条图文尚未完成及已完成范围。

## 产物结构

```text
当前项目/
└── YYYY-MM-DD/
    └── N/
        ├── 内容文稿.txt
        ├── 制作备注.md              # 有参考来源或制作说明时
        └── 配图/
            ├── 生图提示词.md
            ├── 01.png
            ├── 02.png
            └── …
```

## 目录助手用法

```text
python3 <本技能路径>/scripts/prepare_post.py --root <当前项目绝对路径> --date YYYY-MM-DD
python3 <本技能路径>/scripts/prepare_post.py --root <当前项目绝对路径> --date YYYY-MM-DD --reserve
python3 <本技能路径>/scripts/prepare_post.py --root <当前项目绝对路径> --date YYYY-MM-DD --release N --token TOKEN
```

脚本不生成文稿或图片，也不会把目录存在当成已经完成发布。返回的 written_count 表示有文稿的条数，occupied_count 表示已占用的序号数；完整制作状态需要结合提示词中的计划数量和实际图片判断。
